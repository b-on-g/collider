# $bog_collider

Коллайдер менеджеров состояний, в котором остались только $mol и SolidJS. Наследник [$hyoo_js_perf](https://github.com/hyoo-ru/perf.js.hyoo.ru): тот же раннер, тот же граф из статьи [«Big State Managers Benchmark»](https://habr.com/ru/articles/707600/), из 33 вариантов оставлены четыре.

Открыть: https://b-on-g.github.io/collider/

| Вариант | Что внутри |
| --- | --- |
| 🤓⏰ `$mol_wire_solo` | классы с мемо-свойствами, как пишут приложения на $mol |
| 😵⏰ `$mol_wire_let` | те же атомы на замыканиях |
| 😵🍔 SolidJS 1 | вариант из статьи без изменений, `solid-js@1` |
| 😵⏰ SolidJS 2 | `solid-js@2`: `batch` удалён, эффект двухфазный, синхронное применение через `flush()` |

Пустая ссылка открывает этот набор. Правка любого поля форкает его в синхронизируемый бенчмарк с постоянной ссылкой `#!bench=…`, как в оригинале.

## Устройство

- `collider.view.tree` наследует `$hyoo_js_perf`, меняет только ссылку на исходники.
- `collider.view.ts` подставляет пресет, когда в адресе нет ни `bench`, ни параметров старого формата (`titles`, `sources`, …).
- `preset/preset.ts` код вариантов. Загрузчик в коде кейсов назван `esm()`, а не `require()`: MAM ищет `require( '…' )` по исходникам, в том числе внутри строк, и вклеил бы найденные npm-пакеты в бандл.

## Результаты

Headless Chrome 1234, macOS arm64, `--expose-gc`, 18.11.2026. Один прогон, частоты в операциях в секунду, память в байтах на итерацию.

| Вариант | Размер кода | 🥶 холодный | 🥵 горячий | Память |
| --- | --- | --- | --- | --- |
| `$mol_wire_solo` | 130 | 13 402 | 13 373 | 4–8 |
| `$mol_wire_let` | 96 | 13 955 | 13 897 | 3–5 |
| SolidJS 1 | 114 | 11 121 | 11 454 | 161–172 |
| SolidJS 2 | 116 | 10 074 | 10 830 | 224–294 |

Время уходит на `hard()`, то есть на `fib(18)`. $mol быстрее на четверть, потому что считает меньше: в первом шаге `C()` истинно, и `G` не читает `E`. $mol пересчитывает только `H`, а обе версии Solid пересчитывают `E` и `H` в обоих шагах. Это пункт «пропуск невостребованных вычислений» из статьи, и Solid 2 его так и не закрыл.

Размер пакета целиком по bundlephobia, gzip: `mol_wire_lib` 8,9 КБ, `solid-js@1` 8,6 КБ, `solid-js@2` 49,7 КБ (из них `@solidjs/signals` 43,2 КБ). В приложении на $mol отдельного пакета нет: атомы входят в бандл как модули `mol/wire/*`, и тянутся только используемые.

## Сравнение с Solid 2.0

Пункты взяты из анонса [Solid 2.0: The Long Hold](https://www.solidjs.com/blog/solid-2-0-the-long-hold/), в том порядке, в каком Solid подаёт их как преимущества.

| Что обещает Solid 2.0 | Solid 2.0 | $mol |
| --- | --- | --- |
| Асинхронность внутри графа | `createMemo` принимает Promise и async-итератор, ожидание через `isPending` и `<Loading>`, гонки разрешаются, спекулятивное состояние откатывается | Так устроено изначально. Код пишется синхронно, ожидающий атом бросает Promise, файбер перезапускается по готовности. `$mol_wire_sync` и `$mol_wire_async` переводят API между мирами. Ожидание показывает сам компонент: у вида атрибут `mol_view_error="Promise"` и анимация, `isPending` и `<Loading>` писать не нужно. Устаревший запрос отменяется: у `$mol_fetch` деструктор зовёт `AbortController.abort()`. Отдельного механизма отката оптимистичных записей нет |
| Server Functions в ядре | `"use server"`, RPC через Request/Response, `live` через SSE | Прямого аналога нет. Сервер пишется на `$mol_rest_server`, а для данных есть Giper Baza: CRDT с синхронизацией, приложению серверный код не нужен совсем |
| Диагностика для AI-агентов | стабильные коды ошибок, место в исходнике, ссылка на доку, поиск водопадов и плохих форм графа, Chrome Performance Tracks, плагин Sentry | Кодов ошибок и поиска водопадов нет, здесь Solid впереди. Зато каждый атом назван путём от корня: `$bog_collider.Root(0).Case(3).sample()`, по стеку видно, где упало. Ошибка рисуется на месте сломанного компонента, остальное приложение работает. `$mol_dev_format` показывает атомы в DevTools с текущим значением и подписками |
| Экспериментальный синтаксис | ReactiveScript и TSRX, компилируются | `view.tree` в ходу давно и не экспериментальный: декларативное описание компонентов, компилируется в TS-класс с типами, любое вложенное свойство переопределяется одной строкой |
| Без метафреймворка | SolidStart выведен из употребления, нужны плагины Vite, роутер и кеш сторонние, например TanStack | Метафреймворка не было никогда. MAM сам собирает, проверяет типы, гоняет тесты, поднимает дев-сервер и раскладывает бандлы по платформам. Роутинг в `$mol_state_arg`, кеш в атомах, офлайн в `$mol_offline`, плагинов и конфигов нет |
| Меньший API | удалены `createResource`, `batch`, `startTransition`, `on`, `produce`, `createComputed`, `createMutable`; `createEffect` разделён на две функции | Реактивный API из трёх декораторов: `$mol_mem`, `$mol_mem_key`, `$mol_action`. Эффектов нет вообще: побочное действие тоже атом, его тянет рендер. `batch` не нужен с первого дня, пересчёт отложен до кадра, а чтение синхронно отдаёт свежее значение |
| Диагностика Long Hold | предупреждение, если индикатор ожидания висит долго после ввода | Аналога нет |
| Стабильность | 23 релиз-кандидата, API заморожен с августа, `npm create solid@latest` | Версий нет, все модули живут в одной ветке и обновляются вместе. Каждый пакет на npm пересобирается автоматически (`mol_wire_lib@1.0.1845`). Старт: `npm create view-tree-lsp@latest` или `npm exec mam@latest путь/к/модулю` |

## Чего нет в анонсе Solid, но есть в $mol

Реактивность:

- Невостребованное не считается. В бенчмарке Solid пересчитывает `E`, который никто не читает, $mol нет.
- Структурно равные значения гасятся сами: атом сравнивает через `$mol_compare_deep`. В Solid для этого нужен `{ equals }` и внешняя функция сравнения, в бенчмарке её берут у $mol.
- Ресурсы освобождаются детерминированно. Атом, на который больше никто не подписан, уничтожается сразу и зовёт `destructor()` у своего значения. `onCleanup` не нужен, сборщик мусора не участвует.
- Динамические зависимости: подписки пересобираются при каждом пересчёте, ветка `C() || E()` не держит `E`, пока он не нужен.
- Контекст `this.$` наследуется по дереву объектов. Любую глобальную сущность можно подменить для поддерева или теста без провайдеров.

Компоненты:

- 246 модулей в `mol/`: списки, формы, таблицы, графики, редакторы, больше тысячи иконок, темы. Всё переопределяется строкой в `view.tree`, без форков.
- Список рендерит только видимое, виртуализация включена по умолчанию.
- Стили по атрибутам, которые генерируются из имён свойств, и типизированный CSS в `.view.css.ts` через `$mol_style_define`.
- Локализация встроена: `@ \Текст` в дереве уходит в `*.locale=en.json`, переводы лежат рядом.
- Ошибка или ожидание у одного компонента не роняет страницу: каждый вид сам себе граница.

MAM:

- Ноль конфигов. Зависимость появляется, когда в коде встречается имя `$mol_button` или `mol_button`, путь выводится из имени.
- В бандл попадают только использованные модули, без tree-shaking по импорту.
- Один модуль собирается из TS, `view.tree`, CSS, GLSL и любых других файлов, теги в имени (`.web.`, `.node.`, `.test.`, `.locale=ru.`) раскладывают их по бандлам.
- Тесты лежат рядом с кодом, собираются в `node.test.js` и `web.test.js` и прогоняются при каждой сборке.
- npm-пакеты ставятся сами по `require( '…' )` в коде.
- Монорепозиторий фрактальный: любой модуль выносится в свой репозиторий строкой `pack … git …` в `meta.tree`, сборщик сам его клонирует. Так сделан и этот коллайдер.
- Одна версия всего: конфликтов версий и `peerDependencies` нет.
